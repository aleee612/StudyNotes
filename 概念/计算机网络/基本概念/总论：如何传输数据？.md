### 总论：如何传输数据？

> [!summary] 完整主线
> 接入链路 
> → DHCP 获取网络配置 
> → DNS 解析域名 
> → 判断目的地址是否同网段 
> → ARP 获取下一跳 MAC 
> → TCP 三次握手 
> → TLS 握手 
> → HTTP 请求 
> → 逐层封装 
> → 交换机按 MAC 转发 
> → 边界路由器执行 NAT/NAPT 
> → 路由器按最长前缀匹配逐跳转发 
> → 服务器逐层解封装并响应 
> → NAT 反向转换 
> → TCP 重组、TLS 解密 
> → 浏览器处理资源并渲染页面

以下以主机 A 通过家庭路由器访问公网 HTTPS 服务器 B 为例：
```text
主机 A
IP：192.168.1.10/24
MAC：AA-AA-AA-AA-AA-AA
默认网关：192.168.1.1
临时 TCP 端口：51514

家庭路由器
内网 IP：192.168.1.1
公网 IP：203.0.113.5

服务器 B
域名：www.example.com
IP：198.51.100.20
HTTPS 端口：443
```

#### 封装与解封装总览

发送端由上至下封装：
```text
HTTP 消息
   ↓ TLS 加密
TLS 记录
   ↓ TCP 封装
TCP 报文段
   ↓ IP 封装
IP 数据报
   ↓ 以太网封装
以太网帧
   ↓ 物理层
比特 / 电磁信号
```
接收端按相反方向逐层解封装

常用名称与传输单位：

| 层次 | 主要任务 | 常用数据单位 | 典型标识 |
| --- | --- | --- | --- |
| 应用层 | 提供具体网络服务 | 报文/消息 | 域名、URL、应用协议字段 |
| 传输层 | 进程到进程通信 | TCP 报文段、UDP 用户数据报 | 端口号 |
| 网络层 | 主机到主机、跨网络转发 | IP 数据报 | IP 地址 |
| 数据链路层 | 相邻结点间传输 | 帧 | MAC 地址 |
| 物理层 | 传输比特 | 比特 | 电气、光学或无线信号 |

### 接入网络与 DHCP

主机刚接入网络时，通常还不知道自己的 IPv4 地址、子网掩码、默认网关和 DNS 服务器，因此先运行 [[DHCP]]
#### DHCP DORA 过程
DHCP 是应用层客户—服务器协议
使用 UDP：
	服务器端口 67，客户端端口 68
##### DHCP DISCOVER
客户端尚无可用 IPv4 地址，也不知道服务器位置，通常发送广播：
```text
DHCPDISCOVER
→ UDP（68 → 67）
→ IPv4（0.0.0.0 → 255.255.255.255）
→ Ethernet（主机 MAC → FF-FF-FF-FF-FF-FF）
```
交换机收到广播帧后向除入端口以外的同 VLAN 端口泛洪。准确地说，是客户端发送广播，交换机负责泛洪，并不是“交换机产生 DHCP 广播”
##### DHCP OFFER
DHCP 服务器提出一套候选配置，例如：
- IPv4 地址及租期；
- 子网掩码；
- 默认网关；
- DNS 服务器地址
##### DHCP REQUEST
客户端声明自己选择的服务器和地址
广播该报文还能使未被选中的服务器知道自己的提议未被采用
##### DHCP ACK
服务器确认租约，客户端正式使用配置
四步速记为：
```text
Discover → Offer → Request → ACK
```
#### DHCP 中继代理
路由器通常不转发本地广播
若 DHCP 服务器在其他子网，中继代理会接收客户端广播并转发给远端服务器，再把响应送回客户端

> DHCP 中继代理不是 DHCP 服务器；中继只负责跨子网转发，地址池和租约由服务器管理
#### DHCP 与后续协议的关系
- DHCP 负责配置网络参数；
- DHCP 不负责解析域名；
- DHCP 不会让主机自动知道其他设备的 MAC；
- DHCP 与 [[NAT]] 相互独立，前者配置主机，后者在边界转换报文地址或端口

### 域名解析 DNS
用户输入：
```text
https://www.example.com/
```

应用程序需要先把域名解析为服务器 IP。查询通常依次利用浏览器缓存、操作系统缓存、hosts 文件以及 DNS 解析器。

若本地没有结果，主机向配置的 DNS 服务器发送查询。传统 DNS 查询通常使用 UDP 53；区域传送、响应过大或需要回退时可以使用 TCP 53，现代环境还可能使用 DoT 或 DoH。

DNS 可能通过递归解析器继续查询：

```text
根 DNS
  ↓
顶级域 DNS
  ↓
权威 DNS
```

最终得到并缓存资源记录，例如：
```text
www.example.com → 198.51.100.20
```

DNS 只负责名称与资源记录的查询，不负责把后续业务数据转发到服务器

---
### 判断目标是否在本地子网

主机使用自己的子网掩码比较网络前缀：

```text
192.168.1.10 AND 255.255.255.0 = 192.168.1.0
198.51.100.20 AND 255.255.255.0 = 198.51.100.0
```

网络地址不同，因此目标服务器不在本地子网，主机选择默认网关 `192.168.1.1` 作为下一跳。

若目标在同一子网，下一跳就是目标主机本身；若目标在其他网络，下一跳通常是默认网关

相关计算详见 [[子网划分与路由聚合]]

### ARP 获取下一跳 MAC

IPv4 数据报在以太网上发送前，需要知道当前链路中下一跳接口的 MAC 地址。若 ARP 缓存没有对应表项，主机发送 ARP Request：

```text
Who has 192.168.1.1?
Tell 192.168.1.10.
```

ARP Request 使用广播目的 MAC：

```text
FF-FF-FF-FF-FF-FF
```

网关收到后通常单播回复：

```text
192.168.1.1 → 网关内网接口 MAC
```

主机把映射暂存到 ARP 缓存
#### ARP 到底查询谁

- 目标在同一子网：查询目标主机 IP 对应的 MAC；
- 目标在其他子网：查询默认网关 IP 对应的 MAC；
- DNS 服务器是否在本地也要先按子网判断，不能无条件说 DNS 查询帧的目的 MAC 一定是网关。

ARP 解析的是本地链路上“下一跳 IPv4 地址 → MAC 地址”，不会查询远端服务器跨越互联网后的 MAC

### 传输层建立 TCP 连接

HTTPS 通常使用 TCP。客户端选择临时源端口 51514，服务器监听 443：

```text
192.168.1.10:51514 → 198.51.100.20:443
```

一个 TCP 连接通常由以下四元组区分：

```text
源 IP、源端口、目的 IP、目的端口
```

若把传输层协议也计入，则常称为五元组。
#### TCP 三次握手

```text
客户端 → 服务器：SYN，seq=x
服务器 → 客户端：SYN+ACK，seq=y，ack=x+1
客户端 → 服务器：ACK，ack=y+1
```

作用包括：

- 确认双方收发能力；
- 同步初始序号；
- 建立连接状态和相关缓存。

TCP 提供面向连接、可靠、有序的字节流服务，依靠序号、确认、校验和、重传、接收窗口和拥塞控制等机制工作

---
### TLS 建立安全信道

访问 HTTPS 时，TCP 建立后还需进行 TLS 握手。不同 TLS 版本流程不同，可把现代流程概括为：

```text
ClientHello
  ↓ 客户端支持的版本、密码套件、随机数、密钥共享等
ServerHello
  ↓ 服务器选择参数并给出密钥共享
Certificate / CertificateVerify
  ↓ 服务器证书与身份证明
Finished
  ↓ 双方验证握手并开始使用会话密钥
```

客户端需要验证：

- 证书链能否追溯到信任的 CA；
- 证书域名是否匹配；
- 证书是否在有效期内；
- 服务器是否持有与证书公钥对应的私钥。

握手完成后，双方主要使用对称会话密钥加密应用数据，因为对称加密适合大量数据传输。

TLS 主要提供：

- 服务器身份认证（也可选客户端认证）；
- 数据机密性；
- 数据完整性；
- 防止传输内容被未授权篡改。

> `HTTPS = HTTP over TLS over TCP`。HTTP 请求并不是在 TLS 握手之前明文发送。

---
### HTTP 请求与 Cookie

TLS 建立后，浏览器发送加密的 HTTP 请求
解密后的逻辑内容例如：
```http
GET /index.html HTTP/1.1
Host: www.example.com
Cookie: uid=123
```
#### Cookie

Cookie 是 HTTP 状态管理机制的一部分

服务器首次响应可以包含：
```http
Set-Cookie: uid=123; Secure; HttpOnly
```

浏览器按域、路径、有效期、SameSite、Secure 等条件保存；后续满足条件的请求可以携带：
```http
Cookie: uid=123
```

并非每个 HTTP 请求都一定携带 Cookie，也不是任意网站都能读取其他域的 Cookie

### 发送端逐层封装
#### TCP 封装
TCP 首部包含：

- 源端口 51514、目的端口 443；
- 序号和确认号；
- SYN、ACK、FIN 等控制位；
- 接收窗口；
- TCP 校验和；
- 可选字段

应用字节流较大时，TCP 会根据 MSS 等条件划分为多个报文段
#### IPv4 封装
IP 层加入：
```text
源 IP：192.168.1.10
目的 IP：198.51.100.20
协议字段：6（TCP）
TTL：例如 64
```

形成 IPv4 数据报。此时目的 IP 是最终服务器，不会因为下一跳是网关就把目的 IP 写成网关地址
#### 以太网封装
由于当前下一跳是默认网关：
```text
源 MAC：主机 A 的 MAC
目的 MAC：默认网关内网接口的 MAC
类型：IPv4
载荷：IPv4 数据报
尾部：FCS
```

核心区别：
```text
目的 IP  = 最终目的主机
目的 MAC = 当前链路上的下一跳
```

---
### 交换机转发以太网帧
交换机收到帧后：

1. 根据源 MAC 学习“该 MAC 位于哪个端口”；
2. 查询目的 MAC；
3. 已知目的端口时只向该端口转发；
4. 未知单播、广播等情况会在相应 VLAN 中向除入端口外的端口泛洪；
5. 若目的端口就是入端口，则过滤该帧。

交换机主要依据 MAC 地址表工作，通常不负责互联网范围的路由选择。交换机每个端口通常形成独立冲突域；VLAN 可以划分广播域。

### 边界路由器执行 NAT/NAPT

家庭路由器收到帧后去掉本段链路层首部，得到 IPv4 数据报。私有地址不能直接在公共互联网中路由，因此边界设备执行 [[NAT]]，家庭网络最常见的是 NAPT/PAT。

原连接：
```text
TCP
192.168.1.10:51514
→ 198.51.100.20:443
```

路由器创建转换表项，例如：
```text
192.168.1.10:51514
↔ 203.0.113.5:40001
```

转换后的报文：
```text
TCP
203.0.113.5:40001
→ 198.51.100.20:443
```

NAPT 至少需要相应更新：

- IPv4 源地址；
- TCP 源端口；
- IPv4 首部校验和；
- TCP 校验和（伪首部包含 IP 地址）。

多台内网主机可以使用相同源端口，NAT 可为它们分配不同的外部端口：
```text
192.168.1.10:51514 → 203.0.113.5:40001
192.168.1.20:51514 → 203.0.113.5:40002
```

NAT 的地址隐藏效果不等于完整安全防护；是否允许连接还可能由状态防火墙和访问控制规则决定。

### 路由选择与逐包转发
#### 控制平面先建立路由

路由信息可能来自：

- 直连路由；
- 管理员配置的静态路由；
- RIP 等距离向量协议；
- OSPF 等链路状态协议；
- BGP 等自治系统间路径向量协议。

可以概括为：
```text
路由选择协议
    ↓ 学习和计算路径
路由表 RIB
    ↓ 选择并安装可用路由
转发表 FIB
    ↓ 数据平面逐包查询
出接口与下一跳
```

OSPF、BGP 等不是每传一个报文就临时重新运行一次；它们在控制平面维护路由，实际报文在数据平面查询已经形成的转发表
#### 最长前缀匹配
假设转发表存在：

```text
198.0.0.0/8       → 下一跳 X
198.51.0.0/16     → 下一跳 Y
198.51.100.0/24   → 下一跳 Z
0.0.0.0/0         → 默认路由
```

目的地址 `198.51.100.20` 同时匹配前三项，路由器选择前缀最长、范围最具体的 `/24`。

默认路由 `0.0.0.0/0` 能匹配任意 IPv4 地址，但只在没有更具体匹配时使用。
#### 普通 IPv4 路由器的每跳处理
1. 检查数据报首部；
2. TTL 减 1；
3. TTL 变为 0 时丢弃数据报，并通常返回 ICMP 超时报文；
4. 因 TTL 改变而重新计算 IPv4 首部校验和；
5. 对目的 IP 做最长前缀匹配；
6. 确定出接口和下一跳；
7. 必要时通过 ARP 获得下一跳 MAC；
8. 使用新链路层首部和尾部重新封装并发送。

---
### 每一跳会改变什么

路径可能是：
```text
主机 A → 家庭路由器 R1 → ISP 路由器 R2 → R3 → 服务器 B
```

普通路由器不会把收到的整个以太网帧原封不动地转发，而是**拆除旧帧并为下一段链路重新封装**

| 字段     | 经过普通路由器时 |
| ------ | -------- |
| 源 IP   | 通常不变     |
| 目的 IP  | 通常不变     |
| TTL    | 每跳减 1    |
| 源/目的端口 | 通常不变     |
| 源 MAC  | 每段链路改变   |
| 目的 MAC | 每段链路改变   |
| FCS    | 每段链路重新生成 |

例外：
- NAT 会修改 IP 地址；
- NAPT 还会修改端口；
- 隧道、负载均衡等设备也可能重新封装或改写相关字段

> IP 地址描述端到端逻辑通信；MAC 地址只在当前链路中用于相邻结点交付

### MTU、分段与 IPv4 分片

具体字段、计算方法和路径 MTU 发现见 [[MTU与IP分片]]；IPv4 与 IPv6 首部结构分别见 [[IPv4数据报]]、[[IPv6]]。

#### TCP 分段与 IP 分片的区别

- TCP 分段发生在发送端传输层，根据 MSS 等限制划分字节流；
- IP 分片发生在网络层，是因为 IP 数据报超过链路 MTU；
- 二者不是同一过程。
#### IPv4 路由器遇到较小 MTU

- `DF=0`：路由器可以分片；
- `DF=1`：不能分片，路由器丢弃数据报并通常返回 ICMP“需要分片”报文。

IPv4 分片规则：
- 同一原始数据报的分片具有相同标识字段；
- MF=1 表示后面还有分片，最后一片 MF=0；
- 片偏移以 8 字节为单位；
- 除最后一片外，分片数据长度通常为 8 字节的整数倍；
- 分片只在最终目的主机重组。

现代网络更倾向使用路径 MTU 发现，让发送端控制报文大小，减少中间路由器分片
IPv6 路由器不执行分片，过大的分组由源主机结合“Packet Too Big”信息处理

### 到达服务器所在网络

最后一台路由器根据最长前缀匹配发现服务器位于自己的直连网络

如果 ARP 缓存中没有服务器的 MAC，就发送 ARP Request，然后封装最后一跳以太网帧：
```text
源 MAC：最后一台路由器出接口 MAC
目的 MAC：服务器 B 的 MAC

源 IP：203.0.113.5
目的 IP：198.51.100.20
```

注意：经过出站 NAT 后，服务器看到的远端地址是 NAT 的公网 IP 和映射端口，而不是主机 A 的私有地址

### 服务器逐层解封装
#### 数据链路层

- 检查目的 MAC；
- 使用 FCS 检测帧在当前链路上的差错；
- 去掉以太网首部和尾部；
- 根据类型字段把载荷交给 IPv4
#### 网络层

- 检查 IPv4 首部及目的 IP；
- 必要时重组 IPv4 分片；
- 根据协议字段 6 把载荷交给 TCP
#### 传输层

- 检查 TCP 校验和；
- 根据目的端口找到服务器套接字；
- 根据序号处理乱序、重复和缺失数据；
- 把连续字节放入接收缓存；
- 返回 ACK，并通过接收窗口实施流量控制

发生丢包时，TCP 可以通过超时或重复 ACK 等机制触发重传；拥塞窗口则限制注入网络的未确认数据量。
#### 应用层

TLS 验证并解密记录后，把 HTTP 请求交给 Web 服务器程序

### HTTP 响应与浏览器渲染

服务器响应例如：
```http
HTTP/1.1 200 OK
Content-Type: text/html
Set-Cookie: uid=123; Secure; HttpOnly
```

响应体可能包含 HTML，也可能要求浏览器继续获取：

- CSS；
- JavaScript；
- 图片、字体、音视频；
- 接口数据。

浏览器解析 HTML、构建 DOM，处理 CSS，执行脚本并完成布局和绘制
获取额外资源时可能复用已有连接，也可能建立新连接，具体取决于 HTTP 版本、域名和连接状态

### 返回方向与反向 NAT

服务器看到的连接对端是：
```text
203.0.113.5:40001
```

因此返回报文为：
```text
198.51.100.20:443
→ 203.0.113.5:40001
```

返回路径不一定与去程完全相同，互联网路由允许不对称路径。

NAT 路由器收到报文后查询转换表：
```text
203.0.113.5:40001
→ 192.168.1.10:51514
```

随后修改目的 IP、目的端口和相关校验和，再通过内网转发给主机 A。主机根据端口 51514 找到原 TCP 连接，完成：
```text
以太网接收
→ IP 处理
→ TCP 排序与重组
→ TLS 验证和解密
→ HTTP 响应交付浏览器
```

没有现存转换表或静态端口映射时，公网主机通常不能任意主动连接到 NAT 后面的内网主机

### 防火墙在过程中的位置

防火墙可能部署在主机、边界路由器或独立安全设备上。常见检查依据包括：

- 源/目的 IP；
- 源/目的端口；
- 传输层协议；
- TCP 连接状态；
- 入接口、出接口和方向；
- 更高层应用特征。

状态防火墙可以允许内部主动建立连接的返回流量，同时拒绝没有匹配状态的外部入站连接。NAT 和防火墙经常集成在同一设备中，但它们是不同功能。

### 数字签名在 TLS 中的作用

数字签名通常是用私钥对消息摘要按签名算法生成签名，而不是笼统地说“用私钥加密摘要”。验证方使用公钥验证签名。

数字签名主要提供：

- 身份真实性；
- 数据完整性；
- 在相应制度和密钥管理条件下提供不可否认性证据。

在 TLS 握手中，服务器可以通过证书和签名证明自己持有对应私钥；批量应用数据仍主要由对称密钥保护

### 一条报文的完整时间线

```text
主机接入链路
  ↓
DHCP 获取 IP、掩码、默认网关、DNS 与租期
  ↓
DNS 把域名解析为服务器 IP
  ↓
主机用掩码判断目标是否同网段
  ↓
选择目标主机或默认网关作为下一跳
  ↓
ARP 获取下一跳 MAC
  ↓
TCP 三次握手
  ↓
TLS 握手、验证证书并建立会话密钥
  ↓
生成 HTTP 请求，按条件携带 Cookie
  ↓
TLS → TCP → IP → Ethernet 逐层封装
  ↓
交换机学习源 MAC、查询目的 MAC 并转发
  ↓
边界路由器建立 NAT/NAPT 映射
  ↓
各路由器递减 TTL、最长前缀匹配并逐跳重新封装
  ↓
必要时处理 MTU、IPv4 分片或 ICMP 差错
  ↓
最后一跳 ARP 获得服务器 MAC
  ↓
服务器逐层解封装、TCP 重组、TLS 解密
  ↓
Web 服务器生成 HTTP 响应
  ↓
响应按相反方向封装和路由
  ↓
NAT 根据转换表恢复内网 IP 与端口
  ↓
主机 TCP 重组、TLS 解密，浏览器处理并渲染资源
```

> [!important] 高频总括
> - DHCP：给主机配置 IP、掩码、网关、DNS 等参数。
> - DNS：把域名解析为 IP，不负责转发业务数据。
> - ARP：在本地链路上解析下一跳 IPv4 地址对应的 MAC。
> - 交换机：根据 MAC 地址在局域网中转发帧。
> - 路由选择协议：在控制平面学习和计算路径。
> - 路由器：在数据平面按最长前缀匹配逐包转发。
> - NAT/NAPT：在网络边界转换地址或端口，并维护状态表。
> - TCP：提供可靠、有序的端到端字节流。
> - TLS：提供身份认证、机密性和完整性保护。
> - HTTP：承载具体的 Web 请求和响应。
